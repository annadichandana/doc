Course Outline: AI-Powered Modern Software Development 2025

This curriculum provides a deep-dive into how AI and large language models (LLMs) are transforming software engineering. Each module (week) below outlines the topics, learning objectives, and key references drawing from the latest industry developments and research, ensuring up-to-date coverage in this rapidly evolving field.

Week 1: Introduction to Coding LLMs and AI Development

Learning Objectives

Understand what large language models (LLMs) are and how they generate code, and learn effective prompt engineering techniques for software tasks. Students will grasp why LLMs have sparked a new paradigm ("vibe coding") in development and how to harness these models responsibly.

Topics & Subtopics

- Foundations of LLMs: What is an LLM actually? – Overview of transformer-based LLMs and their training on code. Emphasize how LLMs serve as a new high-level programming abstraction, projected to deliver trillions in productivity gains in software development[1][2]. - Code-Specific LLMs: Discussion of models specialized for coding (e.g. GPT-4.1, Claude 4, Code Llama-2) and their capabilities as of 2025. Highlight that coding has emerged as one of the most powerful LLM use cases, with AI now able to generate entire functions or files from natural language specs[1]. - Prompt Engineering Basics: How to prompt effectively – techniques to communicate requirements to LLMs. Emphasize clarity and context in prompts: most failures come from ambiguity rather than model limits[3]. Show examples of good prompts vs. poor prompts for coding tasks (e.g. specifying languages, giving function signatures, using step-by-step instructions). - Evolving Best Practices: By 2025, prompt engineering spans formatting, reasoning scaffolds, and role prompting[4][3]. Different models may prefer different prompt styles, so there’s no one-size-fits-all — students learn to iterate and adjust prompts per model for optimal results. - Prompting for Reliability: Introduce idea of “secure prompting” – e.g., explicitly asking for input validation or secure defaults, given LLMs won’t include security or tests unless asked[5][6]. Encourage students to specify constraints (“follow coding standards X”, “avoid deprecated APIs”) in their prompts. - Impact on Development Workflow: Discuss how AI coding assistants (GitHub Copilot, etc.) have changed daily coding. Share recent findings that improved context understanding in AI assistants has doubled acceptance rates of suggestions[7], significantly boosting productivity. Also address limitations: LLMs sometimes produce syntactically correct but subtly wrong code – hence the continued need for human validation and traditional programming knowledge[2][8]. - “Vibe Coding” Concept: Introduce vibe coding (coined 2025) – using natural language to outline what you want and letting the AI produce the code[9][10]. Discuss how this democratizes development (non-experts can create software by describing it) while also raising challenges (like omitted security checks in AI-generated code). Real example: an indie developer launched a game from a single prompt (e.g. “Make a 3D flying game in the browser”) in hours[11]. This illustrates the promise and the need for caution (fast prototyping but potential hidden bugs). Key References: Recent guides on prompt engineering[3], a16z podcast insights on AI’s role in coding[1][2], and case studies of AI-generated projects[11] will underpin this week. Hands-on practice will use an “LLM Prompting Playground” assignment to solidify these concepts.

Week 2: The Anatomy of Coding Agents

Learning Objectives

Decompose an “AI coding agent” into its fundamental components. Students will learn how to build an LLM-based coding agent from scratch, understanding its architecture (planner, tools, memory, etc.), and study the emerging Model Context Protocol (MCP) as a standard for connecting AI to development tools.

Topics & Subtopics

- Agent Architecture & Components: What goes into a coding agent beyond the LLM itself. We cover the standard agentic stack: a planner to break tasks into steps, a controller/orchestrator to manage those steps, tools/API integrations to execute actions (like running code or queries), and a memory/context store for long-term knowledge[12][13]. An agent’s loop of perceive → reason → act is far more than just prompting an LLM. - Planning and Autonomy: Coding agents plan multi-step workflows (e.g. analyze requirement → write code → run tests → fix bugs). We discuss how early autonomous agents (e.g. AutoGPT) revealed planning challenges (tendency to loop without converging)[14][15]. Modern agents use improved planning algorithms to dynamically adjust to errors and avoid infinite loops[16][17]. - Tool Use and Function Calling: How agents invoke external tools/functions. We examine the mechanism of LLM function calls (letting the model trigger predefined actions like filesystem operations or API calls). By 2025 this concept is standardized and widely supported – e.g. OpenAI’s function-calling API (2023) and newer frameworks allow LLMs to call tools like compilers, linters, web search, etc., as part of their reasoning loop[18][19]. This enables agents to compile code, run tests, or query documentation autonomously. - Model Context Protocol (MCP): Introduce MCP as an open standard for connecting AI agents to external systems (tools, data, development environments). Developed by Anthropic & others in late 2024, MCP defines a uniform way for AI clients (like an IDE or agent) to discover and invoke tools with proper context[20][21]. We cover the core ideas of MCP: - Unified Tool Interface: MCP replaces ad-hoc integrations with a single protocol, so an AI agent can plug into many services (code repos, issue trackers, databases) via MCP servers[22][23]. This means instead of custom code for each API, an agent speaks one language to access all (leading to more scalable, maintainable agent design). - MCP Components: MCP servers expose tools/data; MCP clients (our coding agents) consume them. Highlight recent developments: authentication & security in MCP were enhanced in 2025 by collaboration between Microsoft, Anthropic, and identity providers[24]. Now MCP supports delegating auth to OAuth/SSO, allowing enterprise-grade secure agent connections[25]. - Capabilities: Beyond simple tool calls, full MCP spec includes Prompts (pre-defined multi-step workflows servers can provide), Resources (rich outputs like images or logs that agent can manipulate), and Sampling (letting the MCP server itself call language models)[26][27]. Together these transform MCP from just a tool API to a comprehensive framework for building coding agents with shared workflows and data. - Industry Adoption: Discuss how MCP is being adopted in dev tools. VS Code (as of mid-2025) offers complete MCP support, meaning agents in VS Code can use any MCP-compliant tool out-of-the-box[28][29]. Early adopters (GitHub’s coding assistant, Claude Desktop, etc.) show the potential of a rich ecosystem where AI agents readily connect to version control, CI pipelines, or cloud services[30][31]. Students will review an example of building a simple MCP server and client to solidify understanding (as per the “MCP Server Implementations” readings). - Building a Coding Agent (Practicum): The module culminates in a guided exercise: creating a minimal coding agent that uses an LLM to write a function, execute it in a sandbox, and verify output. This ties together planning, tool use, and context. We stress reliability measures, e.g. bounding the agent’s autonomy (max iterations, user approvals) and logging its decisions for debugging. Key References: IBM’s “Anatomy of an AI Agent” design patterns[32][33] and Microsoft’s guidance on AI agent design[34] provide frameworks for agent architecture. The Anthropic MCP announcement[20][21] and VS Code’s June 2025 update on full MCP support[24][27] are referenced to illustrate state-of-the-art agent integration. These sources, along with hands-on labs, prepare students to build and understand coding agents.

Week 3: The AI IDE (Intelligent Development Environment)

Learning Objectives

Learn how modern IDEs integrate AI to create a context-aware, smart coding environment. Students will explore techniques for managing context in large codebases, using AI-powered code understanding, and utilizing AI assistants within IDEs for tasks like code completion, navigation, and design documentation.

Topics & Subtopics

- Context Management in IDEs: How to feed the right code context to an LLM assistant. IDEs now maintain rich workspace context for the AI – rather than naive whole-file prompts, they use embeddings and project indexes to retrieve relevant functions, classes, or docs on the fly. For example, GitHub’s new embedding model (Oct 2025) dramatically improved how Copilot retrieves relevant code: it achieved a 37% boost in relevant snippet retrieval and doubled suggestion acceptance for Java/C# by better understanding project structure[35][36]. We cover how such embedding models work (e.g. Matryoshka Representations that allow multi-granularity code vectors)[37] and how they integrate with IDE search to supply the LLM only the most pertinent pieces of code. - Handling Large Codebases: Discuss strategies like on-demand file reading (the agent opens files as needed), summarizing files into notes, and 100K+ token context windows now available in models (Claude 100k, GPT-4 32k) that let an IDE assistant consider whole modules at once. Trade-offs between long-context vs. retrieval approaches are analyzed. - AI-Based Code Understanding: The IDE as an “AI pair programmer” means it can interpret and explain code to the developer. Students will see demonstrations of asking the IDE, “What does this function do?” or “Find potential bugs in this file,” and getting answers powered by LLM analysis. We reference that multi-agent approaches can enhance code understanding – e.g., one agent generates hypotheses about a bug, another checks them (a technique being researched to improve debugging)[38][39]. Although multi-agent setups are advanced, they hint at how IDEs might run background AI processes to continuously ensure code quality. - PRDs for Agents – AI-aided Design: Product Requirement Documents (PRDs) for agents – this subtopic covers writing high-level specs or design docs that guide AI coding agents. The idea is that rather than diving straight into coding, developers can compose a structured description of features (requirements, acceptance criteria) which the AI will use as a blueprint. We provide a template for a “Design Doc for AI” (as mentioned in the course schedule) and show how feeding this document into the context yields better results (the agent can plan code generation according to the spec). This teaches students an important workflow: using design documentation to steer AI and mitigate the unpredictability of natural language requests. - IDE Integrations and Extensions: Survey of how major development environments incorporate AI: - VS Code & Extensions: GitHub Copilot’s integration in VS Code now includes multiple modes (chat, inline, agent mode). We highlight Copilot Agent Mode (released early 2025) as a case study: from within the IDE, the agent can perform multi-step tasks like refactorings across files, running tests, etc., all under user supervision[18][40]. Key features (context-awareness, tool usage via MCP in VSCode, and UI for user approval of actions) show the maturity of AI IDE assistants[41][42]. - JetBrains and Others: JetBrains IDEs have introduced AI assistants that can explain errors, suggest fixes, and generate code comments. Many come with “bring your own LLM” flexibility by 2025, allowing connection to open-source models. We’ll discuss one example extension that lets developers swap in a local LLM for code completion (underscoring issues of data privacy and cost). - Open-Source AI Dev Tools: Mention projects like Cursor (an open-source AI code editor gaining popularity in 2025), which combine code editing with LLM chat seamlessly[43]. Compare features of open tools vs. commercial (e.g. Cursor vs. Copilot vs. Codeium) to give students perspective on the tooling landscape. - Practical UI/UX for AI in IDE: Best practices for using AI effectively in development: e.g., how to structure an “AI query” in IDE (asking a specific question vs. a vague prompt), when to trust the AI vs. when to manually verify (always run and test the AI-generated code!). We’ll reinforce that formal programming languages and fundamentals remain essential – natural language interfaces are powerful, but understanding what the AI is doing (and being able to code manually when needed) is still critical[2][8]. Key References: GitHub’s InfoQ announcement on embedding-enhanced Copilot[35] illustrates context management improvements. Microsoft’s “Copilot Agent Mode” blog[18][41] provides real-world details of an AI performing IDE tasks autonomously. We also cite research on multi-agent code analysis[39] and a16z commentary on prompt-based vs. traditional programming[1][2] to frame discussion. By the end of Week 3, students will have set up an AI-augmented IDE and practiced optimizing its use (supported by readings like “Coding Agents 101” and labs on IDE setup).

Week 4: Coding Agent Patterns – Autonomy and Collaboration

Learning Objectives

Examine design patterns for AI coding agents, focusing on levels of autonomy and effective human-agent collaboration. Students will learn when to trust an agent to work independently, how to keep a “human in the loop” for critical decisions, and patterns for multi-agent collaboration. The goal is to maximize productivity while maintaining oversight and reliability.

Topics & Subtopics

- Managing Agent Autonomy: Not all AI agents operate with full independence – we explore a spectrum from fully autonomous coding agents to tightly supervised assistants. Key concept: choose the right autonomy level per task based on risk and uncertainty[44][45]. - Autonomy Spectrum: Define levels such as: Manual mode (AI only suggests, human decides), Assist mode (AI handles micro-tasks automatically, e.g. fixing a lint error, but anything major is confirmed by human), Agent mode (AI can attempt whole tasks end-to-end with oversight), up to Fully autonomous (AI writes, tests, and deploys code with minimal human input). Discuss real examples like Copilot’s default vs. agent mode: by Feb 2025, Copilot could autonomously loop on tasks (write code, run tests, fix errors)[18][46], but user approval was required for executing potentially dangerous actions (like running a build command)[42]. This shows a pattern: agents can be given freedom to iterate, but must surface their actions transparently for user review. - Human-in-the-Loop (HITL) Best Practices: Outline scenarios where human oversight is essential – e.g. high-risk changes (security-critical code, payments logic) should always involve code review by a person[47]. Regulations like EU AI Act Article 14 are enforcing human oversight for high-stakes AI decisions[48], which translates to our domain as well. We teach patterns like approval checkpoints (the agent stops and asks for human validation at predefined milestones) and fallback triggers (if the agent is uncertain or errors repeatedly, it hands control back to the dev). - Collaboration Patterns: How do humans and AI agents work together effectively? We introduce design patterns documented by industry leaders: handoff pattern, tool orchestration, co-reviewer pattern, etc.[34]. Illustration: Striking the right balance – an autonomous AI agent (left) can execute code via APIs and automation, but a human-in-the-loop (right) provides oversight, verification, and a “stamp of approval” for high-impact tasks. Modern coding workflows blend AI automation with human judgment for reliability.[44][45] · Handoff Pattern: The agent does what it can, then hands results to a human for final steps. Example: an AI generates a pull request with code changes, but a human developer reviews and merges it. This pattern leverages AI speed while keeping ultimate responsibility with humans (Graphite’s AI code review tool explicitly follows this – “AI will never replace human code review”, it just prepares suggestions[49]). · Pair Programming Pattern: Human and AI work interactively – the developer writes some code, the AI suggests improvements; or the AI writes code and the developer corrects or asks follow-up questions. This is essentially how Copilot Chat and similar “AI pair programmers” function in real time. Emphasize communication: the human should clearly instruct the AI (like one would mentor a junior dev), and the AI should explain its reasoning when asked. · Tool-Orchestrator Pattern: One agent (or component) acts as an orchestrator that can spin up specialized sub-agents or call tools. This pattern appears in frameworks like Microsoft’s AutoGen (multi-agent system)[33]. For coding, it might mean an agent delegates front-end tasks to a UI specialist model and back-end tasks to another, then integrates the results. We discuss how such multi-agent collaboration can solve complex tasks but adds overhead in coordination[50][51]. (Cutting-edge research on multi-agent coding systems and their context-sharing methods[52] is referenced for interested students.) · Examples of Agent Patterns in Practice: · Example 1: Code Review Agent + Developer: An AI code review agent (like Graphite’s “Diamond” reviewer) checks incoming code for bugs and security issues[49]. It leaves comments or suggestions. The human developer then decides which suggestions to accept. This co-reviewer pattern improves code quality and speed: the agent catches obvious issues (Graphite claims its AI finds many bugs before production) while the human focuses on nuanced design decisions. · Example 2: Autonomous Refactoring with Human Approval: Show a scenario with Copilot agent mode performing an across-files refactor (rename a function, update all usages, run tests)[40][53]. The agent completes it, and then the dev reviews the changes via a summary the agent provides. The agent here operates fairly autonomously but within a sandbox (local workspace, tests) and the pattern of oversight is that the dev checks the final diff and test results. Example 3: Error Triage Loop: If an agent encounters an error it can’t resolve, it asks the human a clarifying question (instead of blindly retrying). This pattern ensures the human is pulled in when the agent is stuck, rather than wasting cycles. It’s analogous to a junior dev asking a senior for help when encountering an unfamiliar error – an efficient collaboration tactic. Trustworthiness & Guardrails: A recurring theme is trust – we train students not to blindly trust AI output. Patterns for building trust include: keeping an audit trail of agent actions (logs), using sandboxed execution (so mistakes are contained, see Week 5), and gradual autonomy increase (start the agent on low-risk tasks and only later let it handle critical ones as it proves reliable[54]). We also note that evaluation benchmarks (like AgentBench for multi-step tasks) show AI agents are improving but still not infallible[55]. Thus, adopting a hybrid human+AI workflow is recommended for now[45]. Key References: Skywork’s “Agent vs Human-in-the-Loop in 2025” guide provides a definitive comparison of autonomy levels[44][45] and design patterns with industry examples. We cite Microsoft’s official AI agent design patterns[56] for terminology and the IBM community post on agent anatomy[32] for multi-agent orchestration concepts. Real-world stances from tool makers (Graphite’s CEO on AI vs human review[49]) help underscore the consensus that hybrid approaches outperform purely autonomous or purely manual ones at present. By the end of Week 4, students will be able to identify and implement the right collaboration pattern for a given project and understand the governance needed for safe agent deployment.

Week 5: The Modern Terminal – AI at the Command Line

Learning Objectives

Discover how AI can augment command-line and DevOps workflows. Students will learn about AI-enhanced terminals that execute natural language instructions, how to safely run code in sandboxed environments, and ways to automate scripting and environment setup using AI. The focus is on boosting productivity in the developer’s “terminal” stage of work while maintaining security.

Topics & Subtopics

- AI-Enhanced Command Line Interfaces: The terminal goes intelligent – we examine tools like Warp AI (a modern terminal) that let you type # and describe what you want, and the AI suggests the exact shell commands[57]. This natural-language interface means even complex CLI tasks (setting up Docker, performing grep searches, etc.) can be done by simply describing the goal. We demonstrate an AI CLI assistant parsing a request like “find all TODOs in this project and count them” into the appropriate combination of find/grep commands. Students practice with such tools to get familiar, and we emphasize how this lowers the barrier for using powerful CLI tools (no need to memorize flags). - Agent Mode in Terminal: Discuss Warp’s “Agent Mode” and similar features where the terminal itself hosts an AI agent that can run multi-step workflows without the developer leaving the CLI[58][59]. For instance, you can ask it to “provision a new AWS EC2 instance and deploy my app,” and it will sequentially execute the AWS CLI calls, handle errors, and confirm with you before irreversible actions. This is analogous to Copilot’s agent but in the shell context. - Real-time Guidance: Another pattern – AI can explain command outputs or errors on the fly. E.g., after running a command that errors out, you can ask “Why did that fail?” and get an explanation (the AI reads the error message and uses its knowledge base). This kind of integrated support turns the terminal into a conversational assistant for troubleshooting. - Sandboxed Execution Environments: Running AI-generated commands or code can be risky. We cover best practices for safe execution: sandboxing and isolation. Encourage use of container environments, VM snapshots, or restricted permission sets when letting an AI run commands. For example, an “autonomous execution environment” might use a Docker container where the agent has all needed tools but can’t harm the host system (this was a topic on Mon 10/20) – so if the AI runs rm -rf /, it only nukes the container, not your machine. - Securing the Toolchain: We introduce tools like gating/approval for destructive commands – e.g., require a human to approve if the AI tries to run a command affecting many files or pushing to production. Indeed, VS Code’s AI agent mode required user approval for terminal commands[60]; similarly, Warp’s agent will “ask permission to run commands” it plans[61]. This is a critical safety pattern students must adopt when building AI automation for ops. - Terminal Automation & Scripting with AI: Explore how AI can write and run scripts to automate developer tasks: - Natural Language to Script: Students practice describing a desired script (e.g. “clean up all logs older than 30 days in these directories”) and having an AI generate a Bash or Python script for it. They then test it in a safe environment. This shows AI taking over rote scripting tasks. We cite that as of 2025, LLMs can produce correct small scripts quite reliably (and even self-correct if run iteratively)[62][59]. - Agent Loops for DevOps: For multi-step devops chores, an AI agent can chain commands. Example: deploying an app → The agent might lint code, containerize it, upload to a registry, and update Kubernetes – all guided by one high-level request. We discuss how this differs from traditional shell scripting: the AI can adapt if something fails (e.g., if a deployment fails, it can read the logs and try a fix), essentially acting as a junior DevOps engineer. - Intelligent Terminal UIs: Some new terminals integrate GUI-like prompts driven by AI. For instance, if you type a vague command, the AI might ask follow-up questions in the terminal (“Which AWS region to use?”) to refine the action. This dynamic interaction is new and can make CLI tools more user-friendly. - Guest Insight – Warp’s Vision: We’ll reflect on insights from guest speaker Zach Lloyd (Warp’s CEO) on how AI will change the developer’s command-line experience. Expect discussion on balancing speed and safety: making the terminal ultra-productive with AI (no more Googling command syntax), while ensuring trust (e.g. Warp’s built-in policies to prevent dangerous outputs). Warp’s approach to tracking session state and multi-step flows[63] will be a talking point, highlighting how even terminals now maintain context (like what tasks you’ve completed) to help the AI agent understand what to do next. Key References: Warp’s official blog on AI Command Suggestions and Agent Mode[57][61] exemplifies the state-of-the-art AI terminal. Visual Studio Code’s documentation of requiring confirmation for terminal commands in AI agent mode[60] is used to stress safety. Real anecdotes (e.g., an AI script mistakenly altering a filesystem) drive home why sandboxing is crucial. By working through labs (like an “AI Shell Challenge”), students will gain practical experience in leveraging AI at the terminal while deploying safeguards.

Week 6: AI Testing and Security

Learning Objectives

Understand how AI can both improve software testing and introduce new security concerns. Students will learn to use AI for generating test cases and detecting vulnerabilities, while also studying the security risks of AI-generated code (“secure vibe coding”). The module aims to instill a security mindset when working with AI assistants in coding.

Topics & Subtopics

- AI-Generated Test Suites: Leveraging LLMs to create comprehensive tests. We demonstrate how an AI can generate unit tests from function descriptions or even from code (acting like a diligent QA engineer). Research shows LLM-generated tests can catch many edge cases; for instance, an AI might produce input combinations a human tester didn’t consider. We reference advances like AI-generated fuzz tests and how tools (e.g., Amazon CodeWhisperer’s test generation, or open-source libraries) saw significant improvements by 2025. - Example: Given a simple function, the AI generates multiple unit tests, including boundary conditions. We’ll point out that LLMs, having been trained on vast code, often recall common pitfalls (e.g., off-by-one errors) and write tests for those. However, caution that sometimes AI-written tests can be trivial or mirror the code logic (not truly independent) – hence human oversight is needed to ensure test quality. - Continuous Testing Agents: Introduce the concept of an AI agent that runs in CI pipelines to suggest additional tests or to automatically write regression tests when a bug is fixed (closing the loop on future-proofing). This forward-looking idea is being explored in industry to increase test coverage with minimal developer effort. - Secure Vibe Coding – New Security Challenges: “Vibe coding” (natural-language-driven development) is revolutionary but comes with “silent killer” vulnerabilities[64][9]. We unpack this by examining why AI-generated code often misses security measures: - LLMs aim to satisfy the prompt and may omit checks that aren’t explicitly requested (they’ll happily create a login form but not include rate limiting or strong encryption unless asked)[65]. This leads to security by omission – functional code that passes basic tests but is insecure[66][67]. - Present real examples (from 2025 analysis): e.g., AI-generated code that accidentally hard-coded secrets (API keys) because it followed a training example[65], or an AI-generated password reset function that was vulnerable to timing attacks (the AI used a non-constant-time token comparison)[68]. These were subtle issues that neither the AI nor the initial tests caught. - Shocking Stats: Highlight findings like “40% higher secret exposure in AI-assisted repos”[5] from GitGuardian research and others. Also that many AI-produced snippets include outdated or insecure libraries if not guided otherwise[65]. This impresses on students that AI assistance can accelerate development and mistakes – security must be a conscious part of the process. - Secure Coding Practices with AI: How can we mitigate the above risks? We teach a “holistic secure vibe coding” approach[69][70]: - Secure Prompting: Always instruct the AI about security requirements. For example, instead of “Create a user signup form,” prompt “Create a secure user signup (with input validation, hash passwords, etc.).” Essentially, make security explicit in requirements to counter the AI’s tendency to ignore what isn’t asked[65]. - AI Code Review Tools: Use specialized AI tools (or features in code assistants) that scan AI-written code for vulnerabilities. For instance, the Semgrep for Secure Vibe Coding ruleset[71] can analyze AI-generated code to flag common issues. Students will try running a static analysis (Semgrep or similar) on code they generated with an AI to see what it catches. - Comparative Evaluation of Models: Note that not all LLMs perform equally on security – some (like OpenAI’s or Anthropic’s) have been tuned with more safety guardrails, whereas smaller models might be more prone to insecure suggestions. A 2025 comparison of GPT-4, Claude, etc., showed differences in tendency to include secure defaults[5]. When possible, choose an AI model known for reliability for coding tasks (or at least be more vigilant if using an uncured model). - Human Verification Remains Key: Reinforce that AI does not remove the need for traditional security review. Perform code reviews, use linters, run dynamic security tests (DAST, SAST) on AI-written code. As one industry expert put it: AI can write code, but it won’t secure it unless you ask – and even then you must verify; speed without security is just fast failure[70]. Students should internalize that motto. - AI in Vulnerability Detection: On the flip side, AI is a powerful ally for finding bugs and vulns in code: - Static Analysis and Beyond: Companies like Semgrep (rX) are integrating AI to improve rule-based scanning. AI can help generalize patterns or prioritize findings. E.g., an AI-enhanced scanner might read code and describe in plain English potential issues, making it easier for developers to understand and fix (we refer to insight from Semgrep’s CEO, who spoke on how AI is used to rank the severity of findings). - Penetration Testing Agents: Mention emerging tools where an AI acts as an automated penetration tester – it analyzes an app (code and running instance) trying various attacks. While nascent, this could dramatically scale security testing. For example, an AI fuzz tester might generate hundreds of inputs including ones with SQL injection attempts or XSS, based on learning from known vulnerabilities. - History of Vulnerability Detection: A quick retrospective connecting to “history” topic – from early static analysis (Lint) to advanced tools, now to AI. Show how detection evolved: patterns and rules → ML models (like GitHub’s CodeQL uses some learning) → today’s LLM-based reasoning that can sometimes explain “this code could be exploited if X”. This progression helps students appreciate why AI is the next logical step in code security tooling. - Secure Development Workflow: Synthesize everything into a recommended workflow for students when they use AI for coding: 1. Include security in specs/prompts from the start. 2. Use AI to generate not just code, but also tests and threat models (e.g., ask “what could go wrong with this code?” to let AI enumerate possible issues). 3. Review AI output with tools and manually. Leverage AI code review (like Graphite’s AI Reviews for catching bugs) and then do a human review, especially for critical sections[72]. 4. Continuously learn & update prompts – if an AI repeatedly suggests an insecure practice, adjust your instructions next time (the human is the senior partner in this pair programming). 5. Stay updated – mention that new guidelines (like NIST’s Generative AI Profile 2024) are emerging for AI use; developers should keep an eye on evolving best practices. Key References: The Hacker News article “Secure Vibe Coding: The Complete New Guide”[9][66] is heavily used to illustrate the unique vulnerabilities in AI-generated code and how to address them. Practical insights from Replit and Semgrep blogs[73][71] complement this by providing checklists and tips. We also include research references such as a Stanford study on security issues with Copilot (if any, possibly referenced via the above article) to give weight to claims. After Week 6, students will have practiced generating code with an AI and securing it, plus using AI to audit existing code – leaving them aware of both offense and defense in AI-era software.

Week 7: Modern Software Support – AI for Debugging, Diagnostics, and Docs

Learning Objectives

Explore how AI assists in the maintenance and support phase of software: code debugging, production diagnostics, and documentation. Students will learn to apply AI tools for identifying bugs, performing intelligent code review, generating documentation, and understand trust and reliability considerations (i.e., deciding “What AI code systems can we trust?”).

Topics & Subtopics

- Trusting AI in the Dev Cycle: Open discussion on which AI-generated outputs can be trusted and to what extent. For instance, simple utility functions generated by AI might be fine with minimal review, but complex algorithm implementations require thorough testing. We cover the concept of calibrating trust: start with low trust and gradually increase as the AI proves itself in certain domains. Also mention how certain systems formally verify AI code (e.g., using type checkers, static analyzers to ensure AI hasn’t introduced type errors or obvious issues). - Evaluating AI Suggestions: Provide criteria for evaluating AI-proposed code changes or fixes: Is the change safe? Does it degrade performance? Is it idiomatic? Students learn to critically analyze AI contributions rather than accept them blindly. - Transparency & Explainability: Encourage using AI tools that explain their reasoning. Some new AI debuggers can output a rationale for a fix (“I changed this because...”). If an AI can justify its solution, a developer can gauge trust better. We link this to the concept of intelligible AI, a growing industry focus. - AI for Debugging & Diagnostics: AI can significantly speed up finding and fixing bugs: - Intelligent Debugging Assistants: Tools that take in an error (stack trace, logs, etc.) and suggest the likely cause or even the exact bug in code. For example, given a Python exception and code snippet, an AI might instantly point to an off-by-one error in a loop or a null check missing – tasks that could take a human hours. We demonstrate such an assistant on a sample bug. - Log Analysis: In production, massive logs can be overwhelming. AI systems (like those in APM suites) now ingest logs and metrics to summarize anomalies or correlate events. E.g., an AI might read through an hour of logs and conclude “The service crashed due to null pointer at 14:32 after deployment of version X.” This kind of summary and pinpointing can save engineers time. - Case Study: GitHub’s Augmented Code Review or Graphite’s AI Reviews – these not only look at code changes but also can run the code in their mind (to some extent) to foresee runtime issues. Graphite’s AI code review agent finds critical bugs by simulating usage or leveraging learned bug patterns[72]. Students will get to see a before-and-after: a code review without AI vs. with AI assistance, noting how AI can catch subtle issues (like a missing thread synchronization) that might slip past tired human eyes. - AI for Program Repair: Connect to research where given a failing test, an AI can suggest a code patch to fix it. This overlaps with Week 9 content (automated incident response) but here we focus on the dev perspective (fixing a bug during development). Mention any recent competitions/benchmarks (like the 2025 Code Repair Challenge) where AI systems showed high success rates in auto-fixing bugs – but also discuss their common failure modes (sometimes fixes are one-off and don’t address root cause). - Intelligent Documentation Generation: Maintaining documentation is a classic pain point; AI is now alleviating it: - Code Commenting and Docstrings: IDE-integrated AI can generate docstrings for functions or comments for complex logic. Show how, with one click, a whole file can be annotated with summaries of each function’s purpose, parameters, and examples. Emphasize quality: AI-generated comments should be reviewed for accuracy (sometimes they can describe what the code looks like it does, which might be wrong if code has bugs). - User-Facing Documentation: AI can also draft higher-level documentation: e.g., an end-user README or API docs by analyzing code usage. Students will attempt to have an AI generate a portion of a README and then critique it. Results are surprisingly good for routine descriptions (saving time writing boilerplate docs). We mention tools like Mintlify and AskCodi (2025’s top AI doc tools[74]) that integrate with codebases to continuously update documentation as code changes. - Contextual Q&A Documentation: Perhaps the most powerful: documentation chatbots. Sourcegraph’s Cody or similar can answer questions about the codebase (“Where is the login logic implemented?” or “What does function X do under the hood?”) by combining code search and LLM reasoning. This effectively turns the codebase into a conversational knowledge base, reducing the need to write extensive docs. We explain how these systems use embeddings of the code and retrieval (as seen in Week 3) to generate answers grounded in actual code[75]. - Maintaining Trust in Docs: One must ensure documentation stays in sync with code. We discuss how AI can also help here – e.g., an agent that flags if a function’s behavior changed but the old docstring remains, by rechecking docs against code. Always round back to the theme of trust but verify – documentation generated or updated by AI should be validated (preferably via tests or manual use) to prevent propagating misunderstandings. - AI in Modern Code Reviews: Given Monday’s class on AI code review, we formalize how to integrate AI into the review workflow: - AI Reviewer Role: Position the AI as a junior reviewer: it adds comments and suggestions, but a human reviewer (owner or senior dev) makes final decisions. This aligns with Graphite’s stance that AI aids but does not replace human judgment[49]. - Benchmarking AI Reviews: Share results like the “AI Code Review Benchmarks 2025” which compared multiple AI review tools across real bugs[76]. These showed AI can catch a significant portion of issues (sometimes >50% of typical review comments), especially low-hanging fruit (style, simple bugs). However, AI might miss design-level feedback or could suggest overly pedantic fixes. The takeaway: AI reviews improve baseline code quality and save reviewer time, but cannot assess every nuance or the broader context of why code is written a certain way[49]. - Developer Trust in AI Feedback: Discuss how developers perceive AI feedback – initial studies show developers accept AI code suggestions more when they come with explanations or confidence scores. As such, some tools now indicate likelihood of correctness for each suggestion. We encourage students, as future team leads, to establish guidelines: e.g., don’t auto-merge AI-suggested fixes without running tests, treat AI comments as advisory, etc. Key References: We draw on Graphite’s platform (AI code reviews)[72][49] and possibly a talk by Graphite’s CPO (Tomas Reimers) to illustrate real-world adoption of AI in code review. For debugging and production diagnostics, we reference AI SRE use-cases bridging into Week 9 (like AIOps tools that do root-cause analysis – see NeurBird’s AI SRE description[13][77]). The Index.dev list of documentation tools[74] and any recent case study (e.g., a team using an AI chatbot for internal docs) will be cited. By the end of Week 7, students will have an understanding of how AI can support the “long tail” of development (maintenance and support), and will have experimented with at least one AI code review and one doc generation tool on their project.

Week 8: Automated UI and App Building

Learning Objectives

Investigate how AI accelerates UI/UX design and full-stack application development. Students will experience tools that convert natural language or design mockups into interfaces, enabling “design for everyone.” They will learn rapid prototyping techniques using AI and consider the implications for frontend developers and designers.

Topics & Subtopics

- Design and Frontend for Everyone: AI is lowering the bar to create user interfaces. We showcase systems where a user can simply describe an app or draw a rough sketch, and AI generates a working UI. - Text-to-UI Generation: Demonstrate a tool (e.g., Galileo AI or a Figma plugin with GPT-4 Vision) that takes a prompt like “A mobile signup screen with email and password, and a submit button” and outputs a ready-to-use UI layout or code. Even non-developers can now get a basic UI in minutes. In fact, GPT-4’s vision model can translate hand-drawn wireframes into functional website code[78], illustrating how design prototyping is sped up. - AI-assisted Design in Figma/Adobe: Discuss how design software integrates AI – e.g., suggesting design variations, auto-generating icons or color themes from a description. Designers can iterate more rapidly: “Make this screen more playful” could prompt an AI to adjust styles or layouts creatively. This democratizes design work; however, emphasize that design principles (UX fundamentals) are still needed so that an AI-generated UI is user-friendly (AI might produce a layout, but a human ensures it makes sense for users). - Accessibility by Design: A noteworthy advantage – AI can be instructed to produce accessible UIs (proper contrast, alt text, semantic HTML). By including accessibility in prompts, even those unfamiliar with accessibility standards can get compliant designs, thus “frontend for everyone” includes differently-abled users and developers lacking UX expertise. - Rapid UI/UX Prototyping and Iteration: How AI enables extremely fast prototyping: - One-Prompt Apps: Explore the concept referenced by a16z “One Prompt, Zero Engineers”[79] – internal tools or MVPs built by feeding requirements to an AI agent. Imagine a PM typing “Create a simple inventory management web app with a product list, detail view, and restock form” – the agent could generate a working prototype: UI code, database schema, etc. This is becoming plausible with advanced agents orchestrating multiple steps (as we saw in agent patterns). We evaluate a case where this was attempted (Pieter Levels’ AI-built app from Week 6’s vibe coding example[11] is one such case study – a game prototype in hours). - Multi-Modal Prototyping: Combine image and text: e.g., designer draws a storyboard on paper, snaps a photo, AI generates React code for it. Then you can refine via text: “Change the header to blue and add a logout button” and AI updates the code accordingly. This iterative loop drastically cuts down prototype time from days to hours. - UI/UX Iteration with AI: In traditional design, multiple iterations with user feedback are needed. AI can accelerate this by quickly producing variations. For instance, after deploying a prototype, suppose users find the layout confusing – a developer can ask the AI to “redesign this page for better clarity” and get alternate versions (maybe moving a sidebar, enlarging fonts, etc.) in moments. While AI might not magically produce the perfect design without guidance, it serves as a supercharged assistant for trying ideas. We also introduce how A/B testing can be integrated: AI can generate variant A and B of a UI which can then be tested with users to pick the best, significantly streamlining the UX improvement cycle. - End-to-End App Generation: Pushing boundaries, we discuss systems that attempt to generate an entire application (frontend + backend) from a high-level spec: - Full Stack Agents: An agent that, given a prompt, can scaffold a project (set up a repo, generate frontend code, backend API, database config). By 2025, early versions of these exist – e.g., StackBlitz “Codeflow AI” (hypothetical example by Eric Simons’ team) or experimental open-source projects that built small apps entirely with AI. We examine what they can and cannot do: They excel at boilerplate and standard CRUD apps, but struggle with complex business logic or novel algorithms (which require human insight). - “Single-Prompt Apps” Guest Insights: Eric Simons (guest speaker) shared how their platform allowed building a full app with a single prompt. We relay his key points: focusing AI on repetitive scaffolding frees developers to concentrate on unique features; however, he likely cautioned that maintaining these AI-generated apps still needs engineering effort (particularly to clean up or optimize the initial code). We also address maintainability: AI might produce code that works, but is it clean and idiomatic? Possibly not, so part of the engineer’s new job is refactoring AI-generated code for long-term health (this ties back to trusting AI code). - Frontier: Multimodal and Continuous Apps: Mention any notable research like Meta’s 2025 framework that takes user stories and continuously updates an app as requirements change (if such exists). This would show students the trajectory – that eventually, describing what you want in natural language could result in a living app that evolves, with the AI doing the heavy lifting and the human providing high-level guidance and corrections. This is essentially “software development 10x faster”, but also changes the role of developers to more of architects and curators of AI output. - Implications and Ethics: With “app in a prompt” possibilities, what does this mean for software roles? We pose questions: If anyone can build a basic app via AI, do we devalue frontend developer skills or do those roles shift to focusing on custom, complex interactions that AI can’t easily handle? Likely the latter – AI takes care of routine UI assembly, while developers focus on innovative UX, performance tuning, and integrating with complex systems. We also discuss IP/licensing concerns: AI might inadvertently clone known designs or code from training data; developers need to be mindful of what they deploy (e.g., using an open-source model that might output snippets of GPL code could pose legal issues). This highlights that human oversight isn’t just technical but also legal/ethical. Key References: Andreessen Horowitz’s article “One Prompt, Zero Engineers”[79] encapsulates the vision of AI-built internal tools and will be cited to spark discussion. DataCamp’s notes on GPT-4 Vision building a website from an image[78] provide concrete evidence of AI’s design-to-code ability. We’ll reference any known product announcements (e.g., a demo by Google’s Gemini or Microsoft’s Designer tool in 2025 that generates frontends) to ensure freshness. After Week 8, students will have tried creating a mini app UI with AI and will have a grounded sense of how far they can push these tools, and where human creativity and diligence remain irreplaceable.

Week 9: Agents Post-Deployment – Monitoring, Observability, and Ops Automation

Learning Objectives

Focus on the deployment and operations phase of AI-assisted development. Students will learn how to monitor AI systems in production, use AI for observability (analyzing logs/metrics), and implement automated incident response with AI agents. They will also cover how AI assists in triaging issues and debugging live systems.

Topics & Subtopics

- Monitoring and Observability for AI Systems: After deploying an AI-driven application or agent, keeping tabs on its behavior is crucial. We cover what new things need monitoring: not just traditional metrics (CPU, latency) but also AI-specific metrics like model response time, accuracy of outputs (if measurable), and unusual patterns (like an agent making too many attempts on a task). - AI System Telemetry: Introduce tools that log each decision an AI agent makes (for example, logging each tool invocation and result for an AI coding agent in production). These logs allow developers to later audit what the AI did if something goes wrong. We discuss storing prompts and responses (with care for sensitive data) as part of observability – this is analogous to capturing stack traces for later debugging of AI behavior. - Automated Monitoring with AI: Interesting loop: using AI to monitor AI. Explain how anomaly detection can be enhanced by AI – e.g., an AI can watch metrics dashboards and describe anomalies in plain English. Some SRE tools have alerting systems where instead of a static threshold, an AI considers seasonality and multiple metrics to decide “this situation is abnormal”. - Example: An e-commerce app with an AI recommendation engine – how to monitor that the AI isn’t giving weird recommendations? Possibly track metrics of engagement and have an AI flag if they drop sharply. Similarly, monitoring drift in model inputs/outputs: if an AI agent’s output length or sentiment distribution changes, it might indicate a problem (maybe it’s getting unexpected input). - Automated Incident Response: A highlight of this week – how AI can automatically handle certain incidents. Building on the AI SRE concept: - AI SRE Agents: As introduced by NeuBird’s “AI SRE” concept, these are domain-specific agents for operations that can investigate issues and even trigger fixes[13][77]. We cover the architecture of such an agent: it receives alerts, gathers data (logs, metrics, traces) from various sources, identifies the likely root cause, and suggests or applies a remedy[80][77]. - Reducing MTTR: Emphasize how these agents aim to drastically cut Mean Time To Resolution. NeuBird’s Hawkeye, for example, claims to reduce MTTR by up to 90% by quickly correlating signals and recommending actions[81]. We might simulate an incident: e.g., a web service is down – an AI agent looks at error logs, sees a database connection failure, recognizes from past knowledge that it might be due to max connections reached, and suggests “restart connection pool or increase limit” within minutes. In contrast, a human might take an hour gathering that info from different dashboards. - Actionable Remediation & Guardrails: It’s crucial that if AI is allowed to act (auto-remediation), it does so carefully. We outline that initial deployments of AI ops agents often run in recommendation mode (they propose actions to on-call engineers) until trust is built and maybe eventually some low-risk actions are automated (like auto-scaling a service when traffic spikes). We also mention no-regret actions – an AI might be allowed to do things that are easy to roll back (restart a service) but not, say, alter code. Even with advanced AI, human override/kill-switch is maintained as a best practice[82]. - Integration with DevOps Tools: Show how AI incident response integrates with existing tools – e.g., the agent might post an analysis in Slack or PagerDuty incident notes, and even take input from engineers (“okay, try rolling back deployment”). A cohesive integration is key so that AI augments the on-call team instead of being a black-box. - Triaging and Debugging in Production: AI helps not just in fixing but in organizing and prioritizing incidents: - Intelligent Triage: When multiple alerts fire, an AI can group them if they’re related (e.g., dozens of errors across microservices might all stem from one core database outage – the AI labels them as one incident). Or it can prioritize alerts based on impact (learning from historical incident data what usually is urgent vs. noise). We reference Incident.io’s 2025 guide where AI clusters incidents and even drafts an initial incident report for you[83]. - Root Cause Analysis: A step beyond triage – AI can perform post-incident analysis, reading through all logs and metrics after the fact to pinpoint the trigger. For example, an AI might find “All failures started after deployment #202, likely a bad config pushed at 10:30 AM” by correlating deployment logs with error logs – tasks humans do manually but AI can automate. (Neubird’s list of must-haves included real-time root cause analysis and context-aware learning from past incidents[77][84] – which we’ll cite to emphasize expectations from AI Ops agents.) - Knowledge Retention: As AI agents observe incidents over time, they can build a knowledge base (“When X goes wrong, it’s usually due to Y”). This addresses the common issue of tribal knowledge in ops – the AI becomes a constant team member that remembers past incidents and solutions, even if people leave the team[85][86]. We encourage students to see this as a positive: fewer repeated mistakes, faster resolutions as the AI gets “smarter” with each incident. - DevOps Case Study – Resolve.AI (guest): Mayank Agarwal’s Resolve (if that’s the company) likely builds AI-driven incident response systems. We integrate insights presumably shared: perhaps how AI agents are used in DevOps at scale, maybe an example where their AI handled an issue without human intervention at a major client, or how they ensure reliability and safety in letting AI handle ops. A key point might be trust through incremental adoption: companies start with AI giving suggestions, then automate routine fixes after validation, and so on. - Challenges in AI Ops: It’s not all solved – we talk about limitations: - Hallucinations: If an AI “concludes” something incorrectly (e.g., misreads logs and suggests a wrong fix), it could mislead engineers or, worse, perform a wrong action. That’s why “no hallucinations” is a requirement in incident response[87] – outputs must be based on real telemetry, not guesswork. We mention how vendors are addressing this (e.g., constraining models to only use provided data, and maybe using smaller, more predictable models for analysis rather than giant LLMs that might hallucinate). - False Positives/Negatives: The AI might group things that aren’t actually same issue, or miss linking related issues. It might also not detect a subtle problem until it becomes big (like slowly memory leak). These are areas where human intuition and experience still complement AI. We highlight that the future likely involves human-AI collaboration in SRE much like in development: an AI watches 24/7 and handles straightforward stuff; humans tackle the complex, unprecedented incidents and improve the AI with those lessons. - Trust and Cultural Shift: SREs/DevOps engineers need to trust the AI agent – which involves transparency (the agent showing its reasoning steps, which tools/logs it looked at) and the team validating its decisions over time. There can be resistance (“will the AI take my job or wake me up unnecessarily?”), so part of implementing these systems is proving their value (e.g., show how many hours of toil they saved). Key References: NeuBird’s “Future of DevOps with AI SRE” blog[13][77] is cited to concretely list what AI agents in ops deliver (root cause in minutes, etc.) and the qualities expected (security, accuracy)[87]. Another reference, Top 12 AI Tools for DevOps in 2025[88] or Parity – AI for incident response[89], might be used to name-drop current solutions and their capabilities. By examining real tools (like Parity, Rootly, etc.), students get a feel for how theory meets practice. At the end of Week 9, after possibly a lab exercise simulating an incident with an AI assistant, students should appreciate how AI can make on-call less painful and systems more robust, while also understanding the guardrails and oversight needed.

Week 10: What’s Next for AI Software Engineering

Learning Objectives

Step back and survey the future – upcoming trends, paradigm shifts, and how roles might evolve in the next 5–10 years. Students will contemplate the long-term trajectory of AI in software engineering, including emerging paradigms (e.g., self-healing code, AI-driven requirements gathering) and what skills developers should cultivate to stay relevant.

Topics & Subtopics

- Future of Software Development Roles: Discuss how roles may change when AI is deeply integrated into the development process. - The Evolving Developer: Reinforce that while AI automates many tasks, it augments rather than replaces developers. In fact, AI might elevate the developer role to more of a product thinker or systems integrator. Routine coding could be largely automated, but understanding what to build, architecting the system, and ensuring correctness and security remain human responsibilities. We draw on a16z partners’ discussion: formal programming knowledge (algorithms, languages) will remain essential even if AI writes a lot of code, akin to how knowing math is still needed with calculators[2][8]. - New Roles: Identify emerging roles such as AI Toolsmith/Integrator – developers who specialize in integrating AI into the dev pipeline (for example, customizing an AI model for a company’s codebase). Or Prompt Engineer – though arguably by 2025 prompt engineering is becoming a common skill for all developers, not a distinct job. Possibly AI Auditor – people who review AI system outputs and ensure compliance (especially for high-stakes industries). Students should prepare to wear these hats. - Team Dynamics: How a future dev team might include “AI agents” as team members (e.g., an agent assigned to each human developer as a personal pair, plus agents for testing, ops). This could mean smaller human teams accomplishing what larger teams did before (as hinted by trends of smaller startups building more with AI, etc.). We mention any data, e.g., anecdotal: a startup in 2025 went from needing 5 front-end engineers to 2 because their AI tools handled a lot – freeing those engineers to also focus on product improvements. - Emerging AI Coding Paradigms: - Prompt-Based Programming as a formal paradigm – might we see languages or frameworks specifically for instructing AI (beyond natural language)? For instance, some predict domain-specific prompt languages or higher-level abstractions that combine natural language with formal constraints (like a “software-spec DSL” that an AI can interpret deterministically). We reference any research or early products on this. - Continual Learning and Adaptation: Future codebases may include AI that learns from user behavior in production and updates the software (within set bounds) automatically. E.g., if users frequently trigger a certain error, an AI could suggest a code change to handle that case. This blurs lines between development and maintenance – software might become more self-evolving. We discuss the need for new paradigms to manage this (like policy controls for self-modifying code, and strong tests to avoid regressions). - Multi-Modal and Beyond Code: As AI gets multimodal, devs might increasingly work with UI design, code, and data in an integrated way. Imagine describing a feature with text, drawing a sketch, and the AI producing both the code and design assets. The paradigm of software engineering expands beyond code to orchestrating various AI content generation (images, text for documentation, etc.). - Agentic Systems & AI Services: Perhaps every piece of software can expose an AI agent interface. For example, instead of navigating menus, a user might just ask the software (backed by an LLM) to do something. Developers might then spend time defining the “persona” and knowledge of that agent within their app. This trend could turn UI/UX into more conversational experiences across industries – devs will need to design those interactions, which is a new paradigm blending programming with dialogue design. - Industry Trends and Predictions: Summarize key trends and forecasts: - Productivity Boom vs. Complexity: There’s consensus that developer productivity could 10x with AI assistance in the coming years[1], potentially leading to a “trillion-dollar” impact on the industry (as per a16z)[90]. However, we caution about complexity: software might grow more complex because AI lets us attempt more ambitious projects or inadvertently sprawl code (since generating code is cheap, controlling its quality is the challenge). The future developer must be a “software curator” in this sense, managing complexity that AI can churn out at high speed. - Education and Training: Traditional CS education might evolve – more focus on problem formulation, architecture, ethics, and verification; less on writing boilerplate. But core skills (data structures, computational thinking) remain important as the foundation to effectively use AI (we cite the a16z discussion where they conclude foundational abstractions are still vital[2]). - AI Ethics and Regulation: Predict increased regulation around AI in software (already EU AI Act for some areas[48]). Future devs might need to comply with requirements like documentation of AI-involved processes, bias audits for AI components, etc. This might spawn new tools to automatically produce such documentation (e.g., log what data an AI was trained on, or ensure an AI code generator doesn’t introduce biased outcomes in, say, hiring software). - Convergence of Roles: We might see lines blur between developer, tester, DevOps, and even product manager – as AI takes over execution of tasks, people in all those roles increasingly do similar high-level work: deciding what to build/test/deploy, and letting AI handle the grunt work. Thus, a future “software engineer” might naturally do requirements, code, testing, deployment with AI support in each, rather than those being siloed roles. - Augmented Teams and Smaller Startups: Because AI can do the work of many in seconds (like generating code or tests), teams might remain small but highly productive. It’s predicted that startups or even individual “solopreneurs” can build complex products by leveraging AI for what used to require whole teams[11][91]. The industry could see more one-person companies or very lean orgs succeeding – which is exciting but also means the job market might shift (fewer huge developer teams, more need for those who can operate with AI efficiently). - Grand Challenges and Open Problems: Finally, identify open research questions that today’s students might tackle: - 100% Correctness – Myth or Possible?: Will there be a time when AI can guarantee code correctness (via formal verification combined with generation)? This is the dream of eliminating bugs. While not solved, progress in combining LLMs with formal methods might be on the horizon (point to any 2025 paper or development in that direction, if exists). - General AI in Coding: Could a future AI agent handle an entire software project given just an end goal? What limitations of current LLMs need overcoming (common sense, truly understanding user intent, deeper reasoning over long contexts)? How might breakthroughs in AI (like truly reasoning or improved memory) impact software dev? Possibly discuss the idea of GPT-5 or Claude Next if any rumors, and how increasing model capabilities might finally solve some current pain points (or raise new concerns like AI-generated code all starting to look homogenized). - Human-AI Collaboration Paradigm: The ultimate question: how do we make the collaboration fluid and trustworthy? Perhaps future IDEs will be so advanced that coding feels like talking to a knowledgeable colleague at all times. Productivity could soar, but maintaining human control and understanding is paramount (no one wants to run code they don’t understand). Solving that balance – giving AI more autonomy while keeping humans in the loop meaningfully – is an ongoing challenge (refer back to patterns from Week 4 and note it’s an active area of research and tooling). Key References: For forward-looking content we lean on thought leadership pieces: a16z’s “Emerging Developer Patterns for the AI Era”[92], Martin Casado’s insights (likely shared in class) on how infrastructure is adding AI as a new layer of the stack (from a16z podcast: AI as a new foundational layer)[93]. We also highlight snippets from the “AI Future Is Already Here…”[94] to show optimism about new startups and automation. Finally, we use the course’s concluding slides (Mon 12/1 “Software development in 10 years”) to summarize. Students are encouraged to imagine and prepare for a future where “everyone is an AI-assisted developer” and continuous learning is key.
